# Mama HQ — Safety & Data Constitution (ABSOLUTE)

**This document outranks every other document in the project, including `PRODUCT.md`.** Mama HQ
handles a newborn's logged data and uses AI to organize a parent's life. The rules here are
absolute. When any instinct — helpfulness, cleverness, engagement, convenience — conflicts with
this file, this file wins.

This consolidates and preserves the strongest rules from `.kiro/steering/data-and-ai-standard.md`
and `.kiro/steering/database-standard.md`. Those steering files defer to this document.

---

## 1. Data philosophy — describe recorded data; never clinically interpret the baby

Mama HQ may **report what the parent recorded**. It must **never** draw a clinical conclusion
about the baby's health, adequacy, or development.

**Allowed** (describing recorded data):
- "You logged 8 feeds yesterday."
- "Feeds logged: 61 · Diapers logged: 47 · Sleep sessions logged: 35"
- Counts, durations, history, timelines, and trends *in the recorded data*.

**Not allowed** (interpreting the baby):
- "Your baby is feeding normally." / "Baby isn't feeding enough." / "That's not enough diapers."
- Any diagnosis, medical prediction, or "should" about the baby's body.
- **No scores of any kind** — no baby health score, sleep-quality score, feeding-adequacy score,
  development score, or any derived rating that judges the child.

The line: **describe the user's data; do not clinically interpret the baby.** If a feature would
require judging whether the baby is okay, it does not belong in Mama HQ — that is the parent's
healthcare provider's job.

## 2. AI boundaries

**AI may:**
- Extract intent from free text
- Extract appointments, tasks, shopping items, and questions
- Detect possible memories
- Summarize user-recorded data (counts/durations only)

**AI must not:**
- Diagnose
- Prescribe
- Interpret symptoms
- Diagnose images / rashes
- Determine feeding adequacy
- Determine sleep health
- Diagnose development
- Provide medication recommendations
- Reassure that symptoms are harmless

## 3. AI write model — AI proposes, the user approves, the database commits

AI is an invisible **organizational layer**, not a chatbot and not an autonomous agent. It is
never used for routine logging (that is pure taps).

- The flow is always **propose → review/edit → approve → commit.** There is no "auto-apply."
- Mama HQ must **never** silently create or modify a calendar event, task, list item, question,
  appointment, or any stored record from AI output.
- **Provenance — for every Inbox capture, store and never overwrite:**
  1. the original user input (verbatim, immutable — enforced by a DB trigger),
  2. the AI interpretation,
  3. the proposed actions,
  4. the user's modifications,
  5. the approved actions.
- Use **structured, validated model outputs** (typed JSON), not free-form parsing.
- The AI layer sits behind a **provider-agnostic interface** so the provider can change without
  touching product code.
- AI calls are **server-side only**; the key never reaches the client.

## 4. Clinical content

Any future medical/postpartum/feeding/sleep/safety educational content must be:
- **Separately stored** (its own content system, not mixed into product code or AI prompts),
- **Source-attributed** (authoritative source + URL),
- **Versioned** (content version, effective dates),
- **Reviewable** (review status, reviewed date),
- **Country / region aware**,
- **Never invented dynamically by an LLM.**

No clinical fact is ever generated by the model or improvised by the builder.

## 5. Safety escalation (architectural boundary — do not build a triage engine now)

If a user's free-text input clearly describes a medical emergency, Mama HQ **may** gently surface
*"this may need urgent care — contact your provider or emergency services."* It does **not**
diagnose and does **not** assess severity. Erring toward "seek professional care" is acceptable;
interpreting the baby is not.

The full safety-escalation system is a **future, separate architecture**. It must not be
implemented as medical triage without approved clinical rules. Document the boundary now; build
nothing that assesses severity.

## 6. Privacy & data protection

- **Row-Level Security (RLS) is ON for every table, always**, deny-by-default, scoped to
  `auth.uid()`. There is no table without an explicit policy.
- **Family isolation is mandatory: Family A must never access Family B's data.** The publishable/
  anon key ships to the browser and must be useless without an authenticated session.
- **Data minimization** — collect only what the product needs. Onboarding asks the minimum.
- **Server-side secrets** — the `service_role` key and all AI keys are server-only, never shipped
  to the client, never logged.
- **We do not sell family data. We do not do ad-oriented health tracking.**
- **Account deletion architecture** — a family must be able to delete its account and data;
  cascading deletes are designed in from the schema (ON DELETE CASCADE from `families`).
- **Data export architecture** — a family must be able to export its own recorded data.

## 7. Fail safe

- A write failure surfaces to the user gently and never corrupts client state or crashes the app.
- Reads scope to the current user; a missing/expired session yields "signed out," never another
  family's data.
- A missing/not-yet-migrated optional table degrades gracefully (load the rest), rather than
  taking down the whole app. (See `lib/db.ts` memories handling.)

## The test for every data/AI/security surface (must pass before shipping)

1. Does it only **describe** recorded data, never interpret the baby's health/adequacy/development?
2. Are there **zero** scores/ratings/diagnoses of the child?
3. Does every AI action get **proposed and explicitly approved** before commit?
4. Is the **original input preserved immutably** with full provenance?
5. Is any clinical content **sourced** from authority/review, never invented?
6. Is **RLS on, deny-by-default, scoped to `auth.uid()`**, with no `anon` access to real data?

If a surface can fail any of these, it does not ship.
